# Rivet 框架介绍

## 第 1 页：当前上位机开发的核心痛点

### 传统上位机开发的问题不是做不了，而是界面和状态维护成本高

Qt、WinForms、WPF 都能完成上位机开发，但在实际项目里会遇到几个长期问题：

- UI 表现力有限，复杂布局、图表、主题、动画和现代组件的开发效率不如 Web。
- 页面状态更新麻烦。WinForms、Qt 这类模式下，很多状态刷新需要开发者手动维护；WPF 支持 MVVM，但工程复杂度也会上来。
- 调试 UI 不直观。很难像 Web 一样快速检查布局、样式、状态和组件行为。
- 上位机项目通常不是“前端 + 后端”分工，而是一个人负责设备交互、界面、状态更新和打包交付。
- 设备逻辑和界面逻辑容易混在一起，后期维护成本高。

结论：

上位机开发需要的不是简单换一个 UI 框架，而是把“设备交互”和“用户界面”分到更适合的技术层里。

## 第 2 页：Rivet 的目标

### 设备交互用后端语言做，用户交互用 Web 技术做

Rivet 的目标是把上位机软件拆成两个清晰方向：

```text
与设备交互
  使用后端语言完成
  C# / C++ / Python / 设备 SDK / 算法库
  负责性能、稳定性、硬件调用、业务状态

与用户交互
  使用 Web 技术完成
  Vue / Vite / 图表 / 组件库 / CSS 布局
  负责界面、交互、展示、调试效率
```

这样可以同时获得：

- 后端语言对设备、算法、性能和本地能力的控制力。
- Web 技术在 UI 表现、开发效率、组件生态和调试体验上的优势。
- 桌面应用仍然可以通过 Tauri 壳交付，不要求用户打开浏览器使用。

一句话：

Rivet 希望让上位机开发既保留后端性能，又获得 Web UI 的开发体验。

## 第 3 页：整体结构

### Rivet 的整体结构分为壳子、前端、后端和框架桥接层

```text
┌─────────────────────────────┐
│ 桌面壳 Tauri                 │
│ 窗口 / WebView2 / 打包 / sidecar │
└───────────────▲─────────────┘
                │ 加载前端页面
┌───────────────┴─────────────┐
│ 前端 Vue                     │
│ 页面 / 组件 / 图表 / 用户交互 │
│ 通过 rv 使用后端能力          │
└───────────────▲─────────────┘
                │ Rivet 前端运行时
┌───────────────┴─────────────┐
│ Rivet 桥接层                 │
│ contract / 代理生成 / 状态同步 │
│ 方法调用 / 连接管理 / 重连     │
└───────────────▲─────────────┘
                │ Bridge
┌───────────────┴─────────────┐
│ 后端能力层                   │
│ C# / C++ / Python / SDK / DLL │
│ 设备交互 / 算法 / 业务状态     │
└─────────────────────────────┘
```

说明：

Rivet 本身不是业务框架，也不是 UI 框架。

它做的是把后端能力稳定、低心智负担地暴露给 Web UI。

## 第 4 页：依赖关系和使用方式

### 使用者只关心后端能力和前端页面

业务项目里不需要单独感知一个“桌面壳项目层”。后端项目引入后端核心；前端项目引入前端核心和 CLI，并通过 CLI / 模板接入壳子能力。

依赖关系：

```text
业务项目
  ├─ 后端项目
  │   ├─ 引入 Rivet 后端核心
  │   ├─ 定义设备服务
  │   ├─ 暴露状态变量
  │   └─ 暴露可调用方法
  │
  └─ 前端项目
      ├─ 引入 @rivet/client
      ├─ 引入 @rivet/cli
      ├─ 初始化 createBackend()
      ├─ 页面中直接使用 rv
      └─ 通过 CLI / 模板接入 Tauri 壳能力
```

也可以理解为：

```text
后端项目
  设备逻辑 / 算法 / 状态 / 方法
        │
        │ 引入 Rivet 后端核心
        ▼
Rivet Bridge / contract
        ▲
        │ 由 @rivet/cli 生成前端代理
        │
前端项目
  Vue 页面 / @rivet/client / @rivet/cli / Tauri 壳能力
```

框架核心做的事：

- 后端核心负责扫描后端声明，提供 Bridge 和运行时能力。
- CLI 根据后端契约生成前端 `rv` 代理。
- `@rivet/client` 维护前后端连接、状态同步和方法调用。
- 壳子能力由前端项目通过 CLI / 模板接入，不要求业务项目单独维护一个桌面壳层。
- 后续打包时，前端项目可以通过壳模板把 Web UI 和本地后端组合成桌面应用。

这页的重点：

后端项目仍然像后端项目。

前端项目同时承载 Web UI 和桌面壳入口。

业务开发者不需要单独维护一套通信层或壳子工程。

## 第 5 页：后端能力不限定 C#

### Rivet 的目标是接入整个后端能力，而不是只服务 C#

当前阶段先用 C# 跑通主链路，是因为 C# 在本地服务、SignalR、Source Generator、设备 DLL 调用等方面比较适合先验证框架机制。

但 Rivet 的目标不是“C# 框架”，而是“后端能力到 Web UI 的桥接框架”。

后端能力可能来自：

```text
C#
  本地服务、设备控制、业务状态、主流程

C++
  厂商 SDK、算法库、采集卡 DLL、高性能模块

Python
  脚本、模型、自动化流程、数据处理

其他本地进程或服务
  只要能形成统一契约，前端就不应该感知来源
```

后续接入方式可能有两类：

- 为 C++ / Python 等语言做对应的后端核心包。
- 通过 DLL、PInvoke、外部进程、本地服务等方式接入，再由 Rivet 统一暴露。

关键原则：

前端看到的始终是统一的 `rv`，而不是不同语言的细节。

## 第 6 页：完整使用例子

### 一个设备打开和回调计数的例子

后端负责设备逻辑：

```csharp
public sealed class DeviceService
{
    public Rv<bool> Opened { get; } = new(false);

    public Rv<int> CallbackCount { get; } = new(0);

    [JsCallable]
    public bool OpenDevice()
    {
        _device.Open();

        _device.OnCallback += () =>
        {
            CallbackCount.Value++;
        };

        Opened.Value = true;
        return true;
    }
}
```

前端负责用户交互：

```vue
<script setup lang="ts">
async function openDevice() {
    await rv.device.openDevice()
}
</script>

<template>
    <button @click="openDevice">打开设备</button>

    <div>
        设备状态：{{ rv.device.opened.value ? '已打开' : '未打开' }}
    </div>

    <div>
        回调次数：{{ rv.device.callbackCount.value }}
    </div>
</template>
```

说明：

```text
打开设备       -> 后端方法
设备是否打开   -> 后端状态
回调次数       -> 后端状态
按钮和显示     -> 前端页面
状态同步       -> Rivet 处理
```

## 第 7 页：当前阶段和后续目标

### 当前先把主链路跑通，再扩展语言和交付能力

当前阶段：

- C# 后端声明状态和方法。
- 生成 `rivet.contract.json`。
- 前端生成 `rv.generated.ts`。
- Vue 页面通过 `rv` 使用后端能力。
- SignalR + MessagePack 负责通信。
- Tauri 壳负责桌面化验证。

正在规划或后续补齐：

- 后端事件前端监听，例如设备报警、数据到达、采集完成。
- C++ / Python 后端能力接入。
- sidecar 自动拉起后端进程。
- 更完整的项目模板。
- 更顺滑的开发、调试、打包流程。

最终目标：

后端引包，前端引包，壳子能力由前端项目通过 CLI / 模板接入。

开发者专注设备逻辑和页面交互，不维护中间桥接层。

## 总结页

### Rivet 是上位机后端能力和 Web UI 之间的桥

Rivet 想解决的是上位机开发中长期存在的结构问题：

- 设备交互应该由适合本地能力和性能的后端语言完成。
- 用户交互应该由 Web 技术完成，以获得更好的 UI 表现和开发效率。
- 桌面交付由 Tauri 壳完成，但壳子能力通过前端项目接入。
- 中间的契约、通信、状态同步和代理生成由 Rivet 处理。

一句话总结：

Rivet 让上位机开发者用后端语言写设备，用 Web 技术写界面，同时不被中间通信层拖住。

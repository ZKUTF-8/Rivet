# Rivet 框架工作量与报价拆分

版本：V0.1 评估结构稿 · 日期：2026-09-08

本文件保留此前 Rust 通用核心与多语言方案的工作量拆分，不再作为当前报价依据。当前 C++11 方案的功能、交付节点、维护边界及具体报价初稿见 [框架需求](Rivet框架需求.md)，模块组织见 [框架概要设计](Rivet框架概要设计.md)。

本文尚不是正式报价单。金额、投入人日、日历周期及商务安排，待需求确定后再讨论。数据转换工具另行报价。

## 1. 本次交付为什么需要按框架工程评估

最终使用体验可以很简洁：前端调用一个方法、绑定一个状态，或放入一个文件选择组件。为形成这种体验，框架内部需要完成跨语言类型转换、调用路由、错误处理、状态调度、连接恢复、代码生成和资源管理。

这些公共能力需要在多个项目中重复使用，并在不同语言与约定平台上保持一致。工作量不仅取决于页面和接口数量，还取决于边界条件、平台组合和交付后使用者能否独立接入。

例如，“页面点击启动设备”至少关联语言声明、契约生成、前端类型、调用请求、语言线程调度、业务异常和响应返回；“温度自动刷新”还涉及变化通知、状态合并、缓存上限、连接恢复和最终值一致性。报价按这些实际交付内容拆分，避免单纯按可见控件数量估算。

## 2. 报价组成与计量原则

建议总价由基础交付费用、选购的进阶模块费用、第三方许可费用，以及另行约定的部署／维护服务费用组成。

基础 B01—B08 是完整基础范围；Python、C++、C# 接入均包含其中，分别列价用于说明投入。模块拆价不代表它们都可脱离其他模块独立运行。

每项估算记录需求版本、既有成果复用、剩余设计、编码实现、模块验证、联调交付、外部依赖和验收依据。新增能力与既有成果适配应分别说明，已有完成项不再次按从零实现估算。

**投入人日与日历周期分别列明。** 日历周期按实际投入人数、前后依赖、公司反馈、设备和环境可用时间排定。三种语言不是简单复制，单人实施也不能把可并行阶段按多人同时开发计算。

## 3. 基础模块的工作量构成

### B01 · Rust 通用核心与内置服务

主要工作包括统一运行时与互操作边界设计、通信服务生命周期、请求匹配与调度、线程和资源管理、错误／超时、端口及多实例处理。

交付核心库、公共接口说明和模块测试记录。其工作量主要受运行模式、支持平台、跨语言调用方式和并发要求影响。独立进程与已有宿主集成分别属于额外实现路径，不能默认为同一份工作。

### B02 · 状态同步、节流与事件

主要工作包括快照与状态注册、变化合并、批量推送、最终值保证、可写状态校验、事件通道、慢客户端和有界缓存策略。

交付状态／事件机制、配置说明和时序测试记录。估算重点是数据量、同步语义及异常场景，不以“增加一个计时器”估算整个节流功能。本项计算同步逻辑工作，B01 的通用消息与连接基础不重复计价。

### B03 · Web 核心、契约与开发工具

主要工作包括统一契约格式、TypeScript 类型与代理生成、Vue 状态接入、连接恢复、订阅释放、前端错误反馈以及开发和构建流程。

交付运行时包、开发工具、生成规则和接入文档。本项负责公共契约规范与统一 TS 生成，各语言从自身声明导出契约的工作在 B05—B07 中计算。

### B04 · 文件 IO 与文件选择组件

主要工作包括 Rust 文件模块、后端路径与权限处理、目录数据组织、Web 选择交互，以及模块启用与示例。

交付可复用前后端组件与组件验证记录。组件使用 B01—B03 的既有机制，其通信基础不再次开发计价。文件内容读写、管理操作或上传需求会扩大范围，应按 D04 确认后的清单估算。

### B05 · Python 接入

主要工作包括包加载、声明与状态包装、Python 到统一契约的导出、类型和异常转换、执行环境调度及对象释放。

交付 Python 接入包和语言专项验证。版本、同步／异步支持及数据类型范围影响工作量。Rust 公共核心费用不重复分摊为一份新核心。

### B06 · C++ 接入

主要工作包括互操作接口封装、注册与状态类型、契约导出、回调与内存所有权、编译链接及不同构建配置适配。

交付 C++ 接入接口、封装和构建说明。编译器、运行库、平台架构与对象线程要求影响工作量；不能仅按提供几个导出函数评估完整接入体验。

### B07 · C# 接入与既有链路适配

主要工作包括原生库加载、托管与原生对象生命周期、声明与生成器适配、异步和异常处理，以及迁移说明。

交付 C# 接入包和现有示例的适配结果。先盘点当前 .NET 核心、生成器和 Web 代理可复用的部分，再估算迁移与新增工作；.NET 8、.NET 10 及旧 API 兼容按确认范围计算。

### B08 · Demo、整体验证与交付

主要工作包括共享前端 Demo、三种语言后端 Demo、端到端联调、确认平台的构建／安装验证、稳定性与性能场景、文档整合及交接。

各模块自身的单元或模块验证计入所属模块；跨模块、跨语言和平台整体回归集中计入本项。语言包使用说明由各接入模块编写，本项负责统一启动指南与交付材料整理，避免重复计算。

## 4. 进阶模块的报价方式

### A01 · 波形图表组件

拆分为需求与选型验证、选定图表库的组件封装、数据接入与缓存调度、确认交互功能、性能与持续运行验证、接入文档。

提供开源库和商业库两条候选报价路线。默认选择其中一条完成交付，开发集成费与第三方许可费分列；如果两条路线都要求完成封装和切换，应追加另一条实现与验证工作。

选型验证可以作为本项第一阶段产出，先验证代表性数据规模，再确定后续实现范围。采样通道数、窗口长度、显示点数、游标／多轴／联动等功能变化，均应反映在估算中。

### A02 · 公司风格的上位机 Web 界面框架

拆分为公司界面规范整理、默认主题与布局、确认页面模板、常用组件组合、基础功能集成、屏幕适配、视觉评审修改和使用文档。

以确认的主题数量、页面模板、交互状态、分辨率和评审轮次计算。基础 Demo 的验证界面计入 B08，公司视觉与应用模板建设计入本项；真实业务页面和流程不按“模板”隐含纳入。

若同时选购 A01，其在本套主题中的一次集成与样式对齐需明确归属，建议计入 A02；波形组件本身的实现与性能验证仍归 A01。

## 5. 建议的阶段交付与费用关联

以下是建议的组织顺序，不预设工期或付款比例。阶段金额应从已确认的模块工作中分配，不能在模块总价之上重复增加。

### M0 · 范围和方案确认

确认需求基线、D01—D08、已有成果复用清单、平台组合和验收指标。输出正式模块估算、依赖安排及交付清单。需求和设计工作归入相关模块；如另设独立评估阶段，其费用是否抵扣后续实施费需事先写明。

### M1 · 第一条完整链路

建议优先用已有经验较多的 C# 完成 Rust 核心、Web 核心、生成工具及语言接入的纵向验证。演示方法调用、状态同步、节流、事件与错误处理，并确认整体架构可用于其余接入包。

本阶段只是 B01、B02、B03、B07、B08 的阶段成果，不代表整个基础包完成验收。

### M2 · 三语言与文件组件齐备

完成 Python、C++ 接入及共享文件组件，三个后端分别通过同一前端 Demo 验证统一使用方式。交付各语言构建与接入说明。

### M3 · 基础范围整体验收

在确认环境中执行完整场景、性能与稳定性检查，处理问题并整理源码、包产物、测试记录和交接材料。此时按 B01—B08 验收基础包。

### M4 · 选购进阶模块验收

A01 按性能与交互指标验收；A02 按公司确认的视觉与页面范围验收。按实际资源情况安排在基础接口稳定后开展，各选项单独记录完成条件。

## 6. 正式报价前需收集的输入

- 公司确认的目标平台、语言和工具链版本，以及测试机器与相关环境。
- 具有代表性的变量规模、更新频率、并发调用、波形数据和运行时长。
- 文件选择／IO 功能清单，是否涉及网络目录、远端文件或上传。
- 上位机界面参考、页面模板清单与视觉评审负责人。
- 现有代码及成果可复用、修改、交付和后续维护的约定范围。
- 是否选购图表与界面框架，以及第三方产品采购、部署和费用承担方式。
- 项目对接、需求确认、阶段反馈、交接、缺陷修复期与后续维护安排。

缺少这些信息时，可以先讨论预算范围；正式金额和交付日期应明确所依据的假设。增加平台、语言版本、图表功能、页面模板或部署模式时，应记录需求差异，再评估费用与周期变化。

## 7. 验收与后续工作的划分

按确认基线交付模块及验证证据；不符合已确认要求的问题按约定缺陷处理。新增功能、扩大兼容范围和提高原有指标属于范围变更，单独评估。

正式交付清单应明确源码版本、依赖清单、包产物、示例、文档、测试环境、结果与已知限制。缺陷修复期、响应时间、培训次数和长期维护方式目前尚未确定，不以“交付框架”默认承诺无限期服务。

正式报价以本文件的模块结构为基础填写金额和周期，需求与验收内容以双方确认版本的主文档为准。

## 协议对比分析

### 低负载（≤ 1,000 变量）：几乎没有差异

在 1,000 变量以下，两种协议的平均延迟都在 1~5ms，帧率和吞吐量基本一致。此区间内序列化耗时占比极低，协议选择对性能没有实际影响。

### 高负载（2,000+ 变量）：MessagePack 优势显现

| 对比项 | 2,000 变量 MsgPack | 2,000 变量 JSON | 5,000 变量 MsgPack | 5,000 变量 JSON |
|--------|-------------------|----------------|-------------------|----------------|
| 平均延迟 | 78ms | 91ms | 124ms | 94ms |
| 帧率 | 42 fps | 38 fps | 63 fps | 22 fps |
| 吞吐量 | 84,000/s | 76,000/s | **315,000/s** | 110,000/s |
| 批次数 | 1,137 | 569 | 1,087 | 329 |

关键发现：

- **2,000 变量**：MessagePack 帧率高 10%（42 vs 38 fps），吞吐量高 10%（84k vs 76k/s）。
- **5,000 变量**：差距急剧拉大。MessagePack 吞吐量是 JSON 的 **2.86 倍**（315k vs 110k/s），帧率是 JSON 的 **2.86 倍**（63 vs 22 fps）。MessagePack 在 15 秒内完成了 1,087 批次，而 JSON 仅完成 329 批次。
- JSON 在 5,000 变量时的平均延迟（94ms）看似低于 MessagePack（124ms），但这是因为 JSON 的推送频率已大幅降低（22fps vs 63fps），每批之间有更多空闲时间，延迟反而显得"稳定"。真实的用户体感是 JSON 更卡——因为数据刷新频率低了 3 倍。

### 结论

MessagePack 的优势在高负载时才真正体现。在变量数 ≤ 1,000 的常见场景下，两种协议性能差异可忽略。**建议默认使用 MessagePack**，因为它在极端场景下有明显优势，在低负载时又不会有任何劣势。

## 核心结论

**SignalR + MessagePack 的传输性能远超上位机系统的实际需求。**

即使在极端压力测试下（5,000 个混合类型变量、10ms 间隔全量推送），平均延迟也仅 100~124ms。而在真实上位机场景中：

- 工业 SCADA/HMI 的典型刷新周期为 500ms ~ 1s，100ms 的延迟远低于业务要求
- 操作员对 100ms 以内的延迟完全无感知
- 真实系统中绝大多数画面只涉及几十到几百个变量，处于 1~5ms 延迟的优秀区间

**这意味着在 Rivet 框架的目标场景内，通信传输不会成为性能瓶颈。** 即使是全厂级 5,000+ 变量的大规模监控，只要更新频率控制在 50~100ms（完全满足业务需求），全量推送也绰绰有余。

## 对 Rivet 框架的设计建议

### 1. 全量推送作为默认策略

测试证明全量推送在 5,000 变量规模内完全可行。框架初期直接采用全量推送即可，简单可靠，无需过早优化。

### 2. 差量更新作为可选优化

当变量规模超过 5,000 或有更高频率需求时，可以在 Source Generator 层面支持差量推送（只发送本次有变化的变量）。这是锦上添花而非必需。

### 3. 更新频率分级（后期优化）

真实系统中不同变量对实时性的要求不同：
- 报警/状态变更：立即推送（事件驱动）
- 过程值（温度/压力）：100~500ms 周期推送
- 统计/趋势：1~5 秒周期推送

Source Generator 可以根据 `[JsBindable]` 特性的参数自动分级推送，进一步降低不必要的传输开销。

### 4. 前端按需订阅（后期优化）

HMI 画面切换时，前端只订阅当前可见变量的更新。这不是传输性能的要求，而是减少前端不必要的渲染和内存开销。

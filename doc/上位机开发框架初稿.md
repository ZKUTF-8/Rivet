# .NET + Vue 上位机快速开发框架 — 设想总结

> 日期：2026-03-31
> 状态：概念设计阶段

## 一、背景与动机

在上位机软件开发中，当前主流的桌面 UI 框架（WPF / Avalonia / Qt Widgets）存在以下痛点：

- **布局能力弱**：XAML 的 Grid/StackPanel 远不如 CSS Flexbox/Grid 灵活
- **开发效率低**：XAML + CodeBehind + ViewModel 三文件分散，改 UI 慢
- **调试体验差**：无法像浏览器 F12 那样直观调试布局和状态
- **组件生态匮乏**：可用的第三方控件库远少于 npm 生态
- **UI 表现力有限**：想做好看的界面成本很高

而上位机软件的 UI 本身并不复杂，性能要求不高（10fps 足够），核心复杂度在硬件交互和数据处理。

**核心想法**：后端用 .NET 处理硬件/业务逻辑，前端用 Vue 做 UI 渲染，通过一套"特性标记 + 自动代码生成"机制消除中间胶水代码。

## 二、架构概览

```
Tauri (Rust)              .NET 进程                    Vue (浏览器/WebView)
┌────────────────┐    ┌──────────────────┐    ┌──────────────────────┐
│  系统 WebView2  │    │  硬件 SDK 调用    │    │  Vue 3 + Vite        │
│  窗口管理       │    │  业务逻辑         │    │  ECharts 图表        │
│  系统托盘       │ ←→ │  Kestrel HTTP    │ ←→ │  ElementPlus 组件    │
│  进程管理       │    │  SignalR Hub     │    │  自动生成的后端代理   │
│  ~3MB 打包体积  │    │  Source Generator │    │                      │
└────────────────┘    └──────────────────┘    └──────────────────────┘
     壳子(Rust)              后端(.NET)                前端(Vue)
```

### 为什么选 Tauri 做壳？

| 方案 | 打包体积 | 问题 |
|------|----------|------|
| Electron | ~200MB | 太重，内存占用高 |
| CEFSharp | ~150MB | 只是嵌浏览器，没有框架能力 |
| WebView2 (WPF) | 中等 | 依赖 WPF，Windows Only |
| **Tauri** | **~3MB** | 用系统自带 WebView2，极轻量 |

Tauri 通过 sidecar 机制拉起 .NET 进程，只负责窗口和系统集成。

### 为什么后端选 .NET 而不是 C++？

上位机领域 C++ 确实常见，但作为"框架的后端运行时"，.NET 相比 C++ 有决定性优势：

#### 技术维度对比

| 维度 | .NET (C#) | C++ |
|------|-----------|-----|
| **Web 服务** | Kestrel + SignalR 开箱即用，几行代码起服务 | 需要引入 Boost.Beast / uWebSockets 等第三方库，配置复杂 |
| **JSON 序列化** | `System.Text.Json` 内置，自动序列化任意对象 | nlohmann/json 等需要手动写序列化映射 |
| **编译时代码生成** | Source Generator 是语言级特性，完美集成 IDE | 只有宏和模板元编程，无法生成额外源文件 |
| **依赖管理** | NuGet 一行引用 | CMake + vcpkg/conan，配置地狱 |
| **开发效率** | async/await 原生支持，内存自动管理 | 手动内存管理，异步编程复杂 |
| **硬件 SDK 调用** | LibraryImport / P/Invoke 直接调用 C/C++ DLL | 原生调用，零开销 |
| **反射/元数据** | 运行时可获取类型信息，便于动态注册 | RTTI 有限，无法遍历方法列表 |

#### 行业现状：国内上位机领域 .NET 是绝对主流

在中国的工控/上位机行业，.NET (C#) 的使用量远超 C++，这不是偶然：

1. **人才储备**：国内上位机开发者大部分走的是 VB6 → Delphi → C# WinForms → C# WPF 这条路线，.NET 是他们最熟悉的技术栈。招一个能写 C# 上位机的比招一个写好 C++ 桌面应用的容易得多。

2. **性能瓶颈不在语言**：上位机的瓶颈在 IO（串口、网口、USB 传输速率），不在 CPU 计算。C++ 的极致性能在这个场景里没有用武之地。

3. **硬件厂商生态**：海康、大华、研华、凌华等国内主流工控硬件厂商，SDK 文档和示例代码基本都提供 C# 版本，有的甚至只有 C#。用 C++ 反而得自己封装。

4. **成本因素**：.NET 完全免费，Visual Studio Community 免费。Qt 商用需要 License 费用，对中小工控公司是额外负担。

5. **中小团队居多**：国内工控公司大部分是中小规模团队，C# 的开发效率优势在这类团队中尤为明显。

#### 结论

C++ 在"计算性能"上有优势，但本框架的后端职责是**硬件交互 + Web 服务 + 代码生成**，这些恰好是 .NET 的强项。对于确实需要 C++ 高性能的场景（算法、信号处理），通过 P/Invoke 调用 C++ DLL 即可，性能开销可忽略。

换句话说：**.NET 做调度和通信，C++ 做计算密集型任务**，各司其职。

**框架选择 .NET 作为后端，面向的正是国内最大的上位机开发者群体**——他们不缺后端能力，缺的是做好看 UI 的手段。本框架正好补上这个短板。

## 三、核心机制 — 特性标记 + 自动代码生成

### 3.1 框架的核心价值

开发者只需要做两件事：
1. **.NET 端**：写业务逻辑，打上特性标记
2. **Vue 端**：写 UI，用 `rv` 直接访问后端

中间的 SignalR Hub 方法、TypeScript 类型定义、前端代理函数 —— **全部自动生成，对开发者不可见**。

#### 前端全局访问关键字：`rv`

框架在前端提供一个全局对象 `rv`，在 `app.vue` 或入口文件中一次性导入后，所有组件无需再 import，直接用 `rv.` 访问后端的一切：

```typescript
// main.ts（仅需一次，框架模板已内置）
import { createBackend } from '@rivet/client'
app.use(createBackend({ url: 'http://localhost:9710' }))
```

之后在任何 Vue 组件中：

```vue
<script setup>
// 无需 import 任何东西，rv 是全局可用的
await rv.device.startCollection(1)        // 调用后端方法
rv.device.isCollecting.value              // 读取后端变量
rv.device.onDataReceived.listen(handler)  // 监听后端事件
</script>
```

`rv` 下按后端服务名（去掉 Service 后缀，转 camelCase）自动组织，层级清晰且简短。

#### 生成的代码对用户不可见

Source Generator 生成的中间代码（Hub 方法、TypeScript 代理）存放在构建目录或 `node_modules` 内部，不会出现在用户的源码目录中。用户的项目里看到的只有自己写的业务代码，干干净净。

### 3.2 三种特性标记

#### `[JsCallable]` — 方法调用

```csharp
// ✍️ 开发者写的
public class DeviceService
{
    [JsCallable]
    public async Task<bool> StartCollection(int channel)
    {
        // 硬件操作...
        return true;
    }

    [JsCallable]
    public async Task StopCollection()
    {
        // 停止采集...
    }
}
```

```csharp
// 🤖 自动生成的后端 Hub 方法（Source Generator 编译时产出）
public partial class BridgeHub : Hub
{
    public async Task<bool> DeviceService_StartCollection(int channel)
    {
        var service = _sp.GetRequiredService<DeviceService>();
        return await service.StartCollection(channel);
    }

    public async Task DeviceService_StopCollection()
    {
        var service = _sp.GetRequiredService<DeviceService>();
        await service.StopCollection();
    }
}
```

```typescript
// 🤖 自动生成的 TypeScript 代理（对用户不可见，在 npm 包内部）
export const device = {
  startCollection: (channel: number) => invoke<boolean>('DeviceService_StartCollection', channel),
  stopCollection: () => invoke<void>('DeviceService_StopCollection'),
}
```

```vue
<!-- ✍️ 开发者写的 Vue 组件，无需 import，rv 全局可用 -->
<script setup>
await rv.device.startCollection(1)
await rv.device.stopCollection()
</script>
```

#### `[JsBindable]` — 属性双向同步

```csharp
// ✍️ 开发者写的
public class DeviceService
{
    [JsBindable]
    private bool _isCollecting;

    [JsBindable]
    private double _temperature;
}
```

```csharp
// 🤖 自动生成的后端代码（Source Generator 编译时产出）

// 1. 属性 setter 中自动推送变更到前端
public partial class DeviceService
{
    public bool IsCollecting
    {
        get => _isCollecting;
        set
        {
            if (_isCollecting == value) return;
            _isCollecting = value;
            BridgeContext.PushToClients("DeviceService.IsCollecting", value);
        }
    }

    public double Temperature
    {
        get => _temperature;
        set
        {
            if (_temperature == value) return;
            _temperature = value;
            BridgeContext.PushToClients("DeviceService.Temperature", value);
        }
    }
}

// 2. Hub 中接收前端的属性修改
public partial class BridgeHub : Hub
{
    public void Set_DeviceService_IsCollecting(bool value)
    {
        var service = _sp.GetRequiredService<DeviceService>();
        service.IsCollecting = value;
    }

    public void Set_DeviceService_Temperature(double value)
    {
        var service = _sp.GetRequiredService<DeviceService>();
        service.Temperature = value;
    }
}
```

```typescript
// 🤖 自动生成的 TypeScript 代理（对用户不可见）
export const device = {
  isCollecting: useBindable<boolean>('DeviceService.IsCollecting'),
  temperature: useBindable<number>('DeviceService.Temperature'),
}
```

```vue
<!-- ✍️ 开发者写的 Vue 组件，无需 import，直接用 -->
<template>
  <div>{{ rv.device.isCollecting.value ? '采集中' : '已停止' }}</div>
  <div>当前温度: {{ rv.device.temperature.value }} ℃</div>
</template>
```

.NET 端属性变化 → 自动推送到 Vue；Vue 端修改 → 自动同步回 .NET。

#### `[JsEvent]` — 事件推送（.NET → Vue）

```csharp
// ✍️ 开发者写的
public class DeviceService
{
    [JsEvent]
    public event Action<double[]> OnDataReceived;

    [JsEvent]
    public event Action<string> OnErrorOccurred;
}
```

```csharp
// 🤖 自动生成的后端代码（Source Generator 编译时产出）
// 自动订阅事件并通过 SignalR 广播到前端
public partial class DeviceService
{
    private void __InitEventBroadcast()
    {
        OnDataReceived += data =>
            BridgeContext.PushToClients("DeviceService.OnDataReceived", data);

        OnErrorOccurred += message =>
            BridgeContext.PushToClients("DeviceService.OnErrorOccurred", message);
    }
}
```

```typescript
// 🤖 自动生成的 TypeScript 代理（对用户不可见）
export const device = {
  onDataReceived: useEvent<number[]>('DeviceService.OnDataReceived'),
  onErrorOccurred: useEvent<string>('DeviceService.OnErrorOccurred'),
}
```

```vue
<!-- ✍️ 开发者写的 Vue 组件，无需 import -->
<script setup>
import { ref } from 'vue'

const latestData = ref<number[]>([])
const errorMsg = ref('')

rv.device.onDataReceived.listen((data) => {
  latestData.value = data
})

rv.device.onErrorOccurred.listen((msg) => {
  errorMsg.value = msg
})
</script>

<template>
  <div>最新数据点数: {{ latestData.length }}</div>
  <div v-if="errorMsg" class="error">{{ errorMsg }}</div>
</template>
```

### 3.3 实现技术 — Source Generator

Source Generator 是 .NET 的编译时代码生成机制（Roslyn 编译器插件）：

```
开发者保存代码 (.cs)
    ↓
Roslyn 编译器启动
    ↓
Source Generator 扫描所有 [JsCallable] / [JsBindable] / [JsEvent] 标记
    ↓
自动生成：
  ├── SignalR Hub 方法 (.cs) → 注入编译流程
  ├── TypeScript 类型定义 (.ts) → 写入前端目录
  └── TypeScript 代理函数 (.ts) → 写入前端目录
    ↓
Vite 检测到 .ts 文件变化 → 前端热更新
```

**整个过程对开发者透明**，改完 C# 代码保存，几秒后前端自动可用。

### 3.4 设计目标 — 前后端完全互通

框架的核心目标很简单：**让前后端的变量、函数、事件像在同一个进程里一样互通**，开发者不需要关心通信细节。

#### 第一阶段：后端 → 前端（优先实现）

| 能力 | 后端标记 | 前端使用 |
|------|----------|----------|
| 前端调用后端方法 | `[JsCallable]` | `await rv.device.startCollection()` |
| 后端变量同步到前端 | `[JsBindable]` | `rv.device.isCollecting.value` |
| 后端事件推送到前端 | `[JsEvent]` | `rv.device.onDataReceived.listen(...)` |
| 前端修改同步回后端 | `[JsBindable]` | `rv.device.isCollecting.value = false` |

#### 第二阶段：前端 → 后端（后续扩展）

后续还可以反过来，让后端能调用前端的方法、监听前端的事件：

| 能力 | 说明 | 场景示例 |
|------|------|----------|
| 后端调用前端方法 | .NET 直接调用 Vue 中注册的函数 | 后端通知前端弹出确认对话框、切换页面 |
| 后端监听前端事件 | Vue 触发事件，.NET 收到回调 | 用户关闭页面时后端执行清理逻辑 |

前端变量同步到后端已经在 `[JsBindable]` 中实现，不需要额外机制。

#### 节流与性能优化（后续设计）

当 `[JsBindable]` 属性高频变化时（如实时温度、采集进度），每次变更都通过 SignalR 推送会造成不必要的网络开销。框架需要内置节流（Throttle）机制：

- **默认节流**：`[JsBindable]` 属性变更合并，按固定间隔（如 100ms）批量推送
- **自定义节流**：`[JsBindable(ThrottleMs = 500)]` 允许开发者指定间隔
- **立即推送**：`[JsBindable(Immediate = true)]` 关闭节流，每次变更立即推送
- **批量推送**：同一周期内多个属性变更合并为一条 SignalR 消息，减少网络开销

具体实现方案在编码阶段再详细设计。

## 四、C/C++ 后端支持

对于高性能算法或已有的 C/C++ 硬件库，通过 .NET P/Invoke 桥接：

```
C/C++ 头文件 (.h)                    ← 开发者写的
    ↓  ClangSharp（现成工具自动解析）
.NET P/Invoke 绑定 (.cs)             ← 自动生成
    ↓  Source Generator
SignalR Hub + TypeScript              ← 自动生成
    ↓
Vue 前端直接调用                      ← 开发者写的
```

C++ 端只需用宏标记导出函数：

```cpp
// device_api.h
JS_EXPORT bool start_collection(int channel);
JS_EXPORT double get_temperature();
```

框架自动生成 P/Invoke → Hub → TypeScript 全链路，前端调用方式与纯 .NET 后端完全一致。

## 五、框架交付物与开发体验

### 5.1 设计原则：用户无感知中间层

框架的核心设计原则是**让开发者只看到"后端"和"前端"两层**，完全意识不到中间存在 SignalR、Hub、Source Generator 这些东西。对用户来说：

- **后端开发者**：安装一个 NuGet 包，给方法/属性/事件打标记，写业务逻辑。结束。
- **前端开发者**：安装一个 npm 包，用 `rv.xxx` 访问后端。结束。
- **中间层**：SignalR 连接管理、Hub 方法生成、TypeScript 代理生成、类型映射、节流 —— **全部由框架内部处理，不暴露给用户**。

```
用户感知到的                         框架内部自动完成的（用户看不到）
┌───────────────────┐              ┌──────────────────────────────────┐
│  后端 (.NET)      │              │  Source Generator                │
│  打标记 + 写逻辑   │─── 编译 ───→│  ├── 生成 SignalR Hub 方法        │
│                   │              │  ├── 生成 TypeScript 类型 + 代理  │
└───────────────────┘              │  └── 注入 DI / 路由注册           │
                                   │                                  │
┌───────────────────┐              │  npm 包内部                      │
│  前端 (Vue)       │              │  ├── SignalR 连接管理             │
│  rv.xxx 直接用    │◄── 运行时 ──│  ├── 变量同步 / 事件分发          │
│                   │              │  └── 节流 / 重连 / 错误处理       │
└───────────────────┘              └──────────────────────────────────┘
```

### 5.2 后端：一个 NuGet 包搞定

**包名**：`Rivet`（或待定的框架名）

```
NuGet 包内容（用户不需要知道细节）：
├── 特性定义：[JsCallable]、[JsBindable]、[JsEvent]
├── Source Generator：编译时自动生成 Hub + TypeScript
├── Host 启动器：内置 Kestrel + SignalR 配置
└── BridgeContext：属性推送、事件广播的内部基础设施
```

**用户的使用方式**（极简）：

```csharp
// Program.cs —— 一行启动
var app = RivetHost.CreateApp(args);
app.Run();
```

```csharp
// DeviceService.cs —— 写业务逻辑，打标记
public class DeviceService
{
    [JsCallable]
    public async Task<bool> StartCollection(int channel) { ... }

    [JsBindable]
    private bool _isCollecting;

    [JsEvent]
    public event Action<double[]> OnDataReceived;
}
```

用户不需要：手写 Hub、配置 SignalR、注册路由、写序列化代码。**打个标记就完事了。**

### 5.3 前端：一个 npm 包搞定

**包名**：`@rivet/client`（或待定的框架名）

```
npm 包内容（用户不需要知道细节）：
├── Vue 插件：createBackend() —— 自动建立 SignalR 连接
├── 全局 rv 对象：按后端服务名组织所有方法/属性/事件
├── 内部实现：连接管理、重连、心跳、节流、类型映射
└── TypeScript 类型定义：由后端编译时生成，提供完整智能提示
```

**用户的使用方式**（极简）：

```typescript
// main.ts —— 一行初始化（框架模板已内置）
import { createBackend } from '@rivet/client'
app.use(createBackend())
```

```vue
<!-- 任意组件中，无需 import，直接用 rv -->
<script setup>
await rv.device.startCollection(1)
rv.device.onDataReceived.listen((data) => { ... })
</script>

<template>
  <div>{{ rv.device.isCollecting.value ? '采集中' : '已停止' }}</div>
</template>
```

用户不需要：配置 SignalR 地址、手写类型定义、处理连接断开重连。**装包、初始化、`rv.` 就用了。**

### 5.4 `rv` 全局对象的命名规则

| 后端类名 | 前端访问路径 | 规则 |
|----------|-------------|------|
| `DeviceService` | `rv.device` | 去掉 `Service` 后缀，转 camelCase |
| `CollectionService` | `rv.collection` | 同上 |
| `VideoManager` | `rv.videoManager` | 非 Service 后缀保持原名 |
| `PcieCard` | `rv.pcieCard` | 同上 |

所有标记了 `[JsCallable]`、`[JsBindable]`、`[JsEvent]` 的成员自动挂载到对应的 `rv.xxx` 下，按类分组、按成员名（camelCase）访问。

## 六、与现有方案对比

| 框架 | UI 技术 | 后端 | 桥接方式 | 上位机适用性 |
|------|---------|------|----------|-------------|
| WPF / Avalonia | XAML | C# | 原生 | UI 能力弱 |
| Blazor Server | Razor | C# | SignalR（自动） | UI 层不是 Vue，表现力差 |
| Electron.NET | Web | C# (Node bridge) | IPC | 太重，200MB+ |
| Photino.NET | Web | C# | 手动 | 没有绑定框架 |
| Tauri | Web | Rust | IPC | 后端不是 C#，不适合上位机 |
| **本框架** | **Vue** | **C# (.NET)** | **SignalR + 自动生成** | **专为上位机设计** |

## 八、风险与注意事项

1. **开发时三进程协调**：Tauri dev + .NET 进程 + Vite dev，需要打磨启动脚本
2. **Source Generator 调试**：运行在编译器进程中，调试方式特殊，需要学习成本
3. **双向绑定复杂度**：状态冲突、网络延迟等边界情况需要仔细设计
4. **开源维护成本**：文档、Issue 回复、持续迭代比写代码更消耗精力
5. **TypeScript 生成时机**：需确保 .ts 文件在 Vite 编译前就绑定好，避免构建顺序问题
